# v1.4 — 闸门只对连续同键生效

- **日期**：2026-10-25
- **触发**：作者观察"鸣潮后一个按键优先级挺高，普攻没结束按技能就会放技能"，
  要求时间缓冲**只对连续相同的键**生效
- **性质**：判定规则修正（**改变手感**，减少换键时的无谓等待）

## 1. 背景

v1.3 的时间闸门是**全局**的：任何动作都会占用一段时间，在此之前不接受下一步输入。

但鸣潮的实际规则是：**新动作会直接打断旧动作**。普攻第二段没打完就按技能，
角色会直接放技能，不会排队等普攻播完。

所以 v1.3 在换键时制造了本不存在的等待——玩家按了技能，程序说"还在普攻动画里"，
实际上游戏早就放出技能了。这会造成**提示滞后于游戏**，比不提示更糟。

## 2. 根因

```python
occupy = self._duration_of(action)      # 对每一步都算占用
self._gate_until = now + occupy          # 一律关闸
```

问题不是"该不该有闸门"，而是**闸门的适用范围错了**。

真正需要等待的只有一种情况：**下一颗键还是同一颗键**。
此时游戏不会打断自己，第二次按下会被丢弃或并入当前动作——
这才是需要缓冲（记住这一下、等动作结束再兑现）的场景。

## 3. 改法

```python
def _needs_gate(self, step):
    if step.get("uncancellable"):
        return True                        # 显式声明不可打断
    next_step = 这一步之后真正要按的那一步
    return self._physical_key(step) == self._physical_key(next_step)
```

| 情况 | 例子 | 是否等待 |
|---|---|---|
| 下一步还是同一颗键 | `a → a`、`a → z`（共用攻击键） | **等**，走缓冲 |
| 换了颗键 | `a → e`、`r → a`、`a → 闪` | **不等**，立即推进 |
| 显式 `"uncancellable": true` | 长动画大招 | **等**，换键也等 |

### 3.1 物理键归并

不同动作名可能落在同一颗物理键上：

| 动作 | 物理键 |
|---|---|
| `basic` / `heavy` | `attack`（都是鼠标左键） |
| `intro_1` / `intro_2` / `intro_3` | 各自独立（不同方向键） |
| 其它 | 动作类型本身 |

如果不归并，`a → z`（普攻接重击，同一颗左键）会被当成换键，漏掉需要的缓冲。

### 3.2 留一个出口：`uncancellable`

有些长动画换键也打断不了（典型是大招）。这类步可以标：

```json
{ "type": "ult", "desc": "解放2", "uncancellable": true }
```

默认不标，不影响现有手感。

## 4. 对爱琳莫轴的实际影响

90 步里 89 个相邻转换：

```
同键（走闸门）  34 个    basic→basic 29 / jump→jump 4 / basic→heavy 1
换键（即时）    55 个
```

**大部分转换现在都是松手立刻推进**，只有普攻连打那 29 处还需要等。

模拟 60 步走下来无卡死，平均 241ms/步（同键等待 380ms、换键瞬时）。

### 4.1 连带好处

`durations_ms` 这张表现在基本只需要调 `basic` 一个值——它代表"一段普攻占多久"。
其它类型只有在你给某步标了 `uncancellable` 时才会用到。

## 7. 遗留 / 风险

- **金色进度条现在只在同键连打时出现**。换键既不等待，就没有"还要等多久"可言。
  这是符合新规则的，**不是显示坏了**——如果收到"进度条不见了"的反馈，先确认是不是换键步。
- **`_physical_key()` 的归并表是硬编码的**。未来如果出现"两个动作名映射到同一颗键"
  的新情况（比如手柄扳机同时触发两个），要记得往表里加，否则会漏掉需要的缓冲。
- `uncancellable` 是估的，没有逐个动作验证过——因为它只是"加严"，标错了表现为
  换键时多等一下，不会卡死，所以风险较低。
