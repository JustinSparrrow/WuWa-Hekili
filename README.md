# WuWa_Hekili (鸣潮连招助手) 🎮
**WuWa_Hekili** 是一款受《魔兽世界》知名插件 Hekili 启发，专为《鸣潮》开发的战斗连招辅助工具。它通过在屏幕上叠加透明的“技能流”图标，帮助玩家肌肉记忆复杂的输出轴（Rotation），提升实战 DPS。

**⚠️ 安全声明：本工具仅通过手柄/键盘信号监听实现逻辑跳转，不读取、不修改游戏内存数据，属于“绿色辅助”。但请注意，任何外部覆盖层工具在反作弊系统下均存在理论上的误封风险，请玩家自行承担后果。**

## ✨ 核心特性
- Hekili 风格 UI：横向滚动的技能队列，左侧聚焦当前动作，右侧预告后续技能。
- 智能资源管理： 
  - 多级降级查找：优先查找角色专属动作图，无素材时自动降级使用通用武器图。 
  - 模糊匹配：支持 normal, enhanced, forte, heavy 等关键词自动匹配文件名。
- 生理级手感反馈： 
  - 长短按区分：普攻与重击共用一个攻击键，程序按**按住时长**区分——轻按是普攻，按住达到阈值（默认 0.5s，`config.json` 的 `settings.heavy_hold_time`）才是重击。
  - 判定在**松手瞬间**完成，不靠定时器轮询，零待机开销；手势不对时悬浮窗会闪一下红框，避免"按了没反应"的错觉。
  - 需要长按的步子在图标上角标显示「长按」，一眼就知道这一步要按住。
- 时间轴对齐（v1.2）：
  - **预输入缓冲**：只在**同键连段**（普攻接普攻）时生效——提前按下的键先存着，等当前动作真正结束才兑现；按得太早（超出寿命）视为游戏已丢弃，提示留在原地等你重按。
  - **换键即时生效**：普攻没打完就按技能，游戏里技能会直接打断普攻放出来，程序也不拦，立刻推进。
  - **连按保护**：同一动作在动画期间连点多次只算一次，不会把提示推到几步开外。
  - **并行插入**：当前步是长按类动作（重击蓄力）且后面某一步被声明为可并行时，
    主悬浮窗**上方会多出一个小窗**（青色描边「并行轨 · 可同时」），标明这是另一条
    时间线、现在就可以按。按下后小窗收起，主指针等你松手完成重击再跳过那一步。
    主队列里对应那格只留一圈青色边框，文字提示只放在上面那个小窗，避免两边重复。
  - 当前动作"还要占多久"用**当前格描边上的环形进度**表示：金色弧从 12 点钟方向顺时针填满，满了就能按。
- 暗色玻璃界面（v2.0）：
  - 悬浮窗是一整块胶囊面板：左边常驻**角色头像 + 元素徽记**，右边是四格时间轴，最右侧显示
    「启动轴 03/49 / 切 · 琳奈 / 长按 0.5s」这类信息。
  - 面板、圆角（连续曲率）、阴影、玻璃噪点、金色描边全部用 QPainter 自绘，**不依赖 QSS**，
    Qt 之外没有任何 UI 依赖。
  - 管理窗口统一无边框玻璃外壳，可整窗拖动，Esc 关闭。
  - **夜间 / 日间双主题**：夜间是墨黑玻璃 + 香槟金（打游戏用），
    日间是冷灰蓝白玻璃 + 钢蓝（录制/桌面用）。在「按键设置」顶部一键切换，
    立刻生效并写进 `config.json` 的 `settings.theme`。
  - 预览/截图工具：`python tools/preview_ui.py --shot [--theme light]`，出图在 `docs/ui/`。
- 多轴支持：自动区分“启动轴 (Opener)”与“循环轴 (Loop)”，启动完成后无缝进入循环。 
- 深度手柄兼容： 
  - 支持 Xbox/PS 手柄及线性扳机（目前只适配了Xbox）。 
  - 动态切人提示：根据角色所在的 1/2/3 号槽位，动态显示手柄方向键提示。
- 高度定制化： 
  - 窗口可自由拖动，位置自动保存。 
  - 所有按键映射、角色武器映射、UI 不透明度均可通过 config.json 修改。

## 🛠️ 安装与运行
本项目基于 Python 编写，在运行前需要配置相关的运行环境并安装必要的依赖库。请确保你的操作系统为 **Windows 10 或 11**。

### 第一步：安装 Python 环境
1. 请前往 [Python 官网](https://www.python.org/downloads/) 下载并安装 **Python 3.8 或更高版本**（推荐 Python 3.10+）。
2. **⚠️ 极其重要**：在安装过程中，务必勾选 **"Add Python to PATH"** 选项。

### 第二步：克隆/下载项目
你可以使用 Git 克隆本项目，或者直接下载 ZIP 压缩包：
```bash
# 使用 Git 克隆
git clone https://github.com/JustinSparrrow/WuWa_Hekili.git
```

下载后，进入项目根目录。

### 安装依赖库
由于本项目涉及底层硬件监听、图像处理和 GUI 渲染，需要安装几个核心的第三方库。
在项目根目录（WuWa_Hekili 文件夹下），在地址栏输入 cmd 并回车打开命令行，运行以下命令：
```bash
# 推荐使用 requirements.txt 一键安装
pip install -r requirement.txt
```

主要依赖说明：
- PySide6：用于渲染 Hekili 风格的透明悬浮窗口。
- pygame：用于读取 XInput / DirectInput 手柄信号。
- keyboard & mouse / ctypes：用于监听键盘与鼠标底层的硬件级输入。
- opencv-python (cv2)：用于辅助工具中的图像处理。

### 第四步：权限与启动 (极其重要)
由于《鸣潮》客户端（及其反作弊系统 ACE）通常以高权限运行，为了保证 keyboard 等底层钩子在游戏处于前台时仍能正常监听按键：
1. 必须以【管理员身份】运行！ 
   - 如果你使用命令行启动：请右键点击“开始”菜单，选择 “终端(管理员)” 或 “命令提示符(管理员)”，然后 cd 到项目目录。 
   - 如果你使用 PyCharm / VS Code 等编辑器：请完全关闭编辑器，然后右键点击其快捷方式，选择“以管理员身份运行”。
2. 启动程序：
   - 在管理员权限的环境下，运行：`python main.py`

### 第五步：游戏内设置建议
显示模式：请务必在《鸣潮》游戏设置中将图像显示模式改为 “无边框窗口 (Borderless Windowed)” 或 “窗口化”。如果使用独占全屏，Windows 将无法在游戏画面上方渲染本工具的悬浮窗。


## 📝 如何编写剧本 (Rotation)

在「连招脚本编辑器」里直接写黑话字符串，点「解析并预览图标」即可生成剧本。

### 黑话速查

| 写法 | 含义 |
|---|---|
| `a` `e` `r` `q` `z` `f` `s` `j` | 普攻 / 技能 / 解放 / 声骸 / 重击 / 处决 / 闪避 / 跳跃 |
| `a2` `e3` | 带变体（二段普攻、技能三段），只影响图标匹配，不影响判定 |
| `e+` `e3+` | **长按**：必须按住够久才算这一下 |
| `爱` `忌` `莫` | 切人（写角色英文名或自己设置的代称）|
| `(变奏)` | 切人前缀，显示成「变奏-角色名」|

> `z`（重击）本身已经是长按语义，不需要再写 `+`。
>
> **并行插入没法用黑话表达**——它取决于角色特性，不是动作本身。需要在剧本 JSON 里
> 给那一步手动加 `"parallel": true`（例如爱琳莫轴里琳奈的声骸）。
> ⚠️ 注意：加了手写字段的剧本，**再进编辑器重新解析会把它丢掉**，改完要小心保存。

### 判定规则（决定"轻按/长按"怎么算）

| 动作类型 | 要求 |
|---|---|
| `basic` 普攻 | 必须轻按（时长 < 阈值）|
| `heavy` 重击 | 必须长按（时长 ≥ 阈值）|
| `intro` / `dodge` / `jump` | 按下即推进，不看时长 |
| `skill` / `ult` / `echo` / `execution` | 默认不看时长；写了 `+`（JSON 里的 `"hold": true`）才要求长按 |

两个可调项都在 `config.json` 的 `settings` 下：

```json
"heavy_hold_time": 0.5,      // 长按阈值(秒)
"strict_tap_check": true     // 期望普攻时，按住太久是否判为"打出了重击"而不推进
```

如果你习惯**按住攻击键连续普攻**，把 `strict_tap_check` 改成 `false`，就只卡长按、不卡轻按的上限。

## ⏱ 时间轴：预输入、连按、并行插入

### 为什么需要它

动作游戏里，"我按了键"和"角色打出动作"不是同一件事。角色有前摇、判定、后摇，
动作没播完之前游戏要么把你的输入暂存、要么直接丢弃。v1.0 把按键事件直接当成
"动作完成"，于是出现三种错位：

| 现象 | v1.0 的行为 | 原因 |
|---|---|---|
| 连按跑飞 | 点 5 下推 5 格 | 动画期间游戏只认 1~2 下，程序却每下都算 |
| 预输入空转 | 按早了也推进 | 游戏把太早的输入丢了，程序在自说自话 |
| 双键并行 | 做不到 | 线性链表只能表达"同一时刻只有一件事" |

### v1.3 的模型

```
剧本指针   当前该做哪一步
时间闸门   同一颗键的"冷却"到什么时候
输入缓冲   闸门关着时收到的、键名正确的输入先存着
并行集合   已经被"提前完成"的未来步
```

一次按键的旅程：

```
松手 ──> 键名对得上当前步？
          ├─ 手势（轻按/长按）也对
          │    ├─ 闸门已开  -> 直接推进
          │    └─ 闸门未开  -> 压进缓冲，等闸门开（预输入）
          └─ 对不上当前步 -> 蓄力中允许插入的动作？是就提前完成它
```

#### 闸门只在"连续按同一颗键"时关（v1.3 修正）

鸣潮里新动作的优先级很高——**普攻还没打完就按技能，技能会直接打断普攻放出来**，
闪避更能取消一切。所以"要等动作播完"这件事只对**同一颗键连点**成立（再点一下
普攻不能凭空多打一段）。

于是闸门只在两种情况关闭：

| 情况 | 例子 | 是否关闸 |
|---|---|---|
| 下一步还是同一颗键 | `a → a`、`a → z`（共用攻击键） | **关**，等动作播完 |
| 换了一颗键 | `a → e`、`r → a`、`a → 闪` | **不关**，立刻推进 |
| 显式声明不动画可打断 | `{"type":"ult","uncancellable":true}` | **关**，即使换键也等 |

也就是说：**跨键连打不需要缓冲，程序不该拦**。这份轴里 89 个相邻转换中有 55 个是
换键，现在全部即时响应；只有 34 个同键连段（主要是普攻连打）才走闸门。

- **预输入**：只用在同键连段上。缓冲项有寿命（`input_buffer_ms`），闸门打开时那一下
  若已超时，说明按得太早、游戏早就丢了 —— 那就**不推进**，提示留在原格等你重按。
- **连按**：同一动作的重复输入在缓冲里会合并成一条并刷新时间戳。狂按 5 下，
  闸门一开只消耗 1 次，推进 1 格。
- **并行**：当前步是长按类动作（重击蓄力）且**后面某一步显式声明了 `"parallel": true`**
  时，屏幕上方会浮出一个小窗「并行轨 · 可同时」，显示那一步的图标和按键。
  此时直接按它，那一步会被提前完成、小窗收起；主指针不动，等你松手完成重击后
  才跳过那一步。主队列里对应那格只留一圈青色边框作为关联提示。

> **并行不是按动作类型自动放行的，必须剧本显式声明。**
> 原因很实际：鸣潮里"蓄力中放声骸"是**角色特性**——琳奈可以，莫宁和爱弥斯
> 在同样的重击→声骸位置就不行。按类型自动放行会让不该并行的角色被提前消耗一步。
> 现在 `config` 的 `timing.auto_parallel` 默认是空数组；确实存在全局通用组合时，
> 才往里面加（如 `[["heavy", "echo"]]`）。

> **第二条时间轴是按需启用的**：加载剧本时会先扫一遍，若整个剧本没有任何可并行的
> 地方，这套逻辑和小窗都不会创建（日志写「剧本无并行动作，跳过第二条时间轴」），
> 普通轴零额外开销。扫描会检查启动轴末尾接循环轴开头这个跨界处。

### 配置

`config.json` 里的 `timing` 段：

```json
"timing": {
  "enabled": true,            // 总开关。false 退化成"按一下就推一格"的老行为
  "input_buffer_ms": 250,     // 预输入的寿命；调大更容易吃住早按，也更容易跑快
  "enable_parallel": true,    // 关闭后不再允许蓄力中插入
  "auto_parallel": [],        // 全局允许并行的组合；默认空，靠剧本写 parallel
  "durations_ms": {           // 每类动作的占位时长
    "basic": 380, "heavy": 700, "skill": 520, "ult": 1100,
    "echo": 520, "execution": 600, "dodge": 320, "jump": 280, "intro": 500
  },
  "character_durations": {    // 角色级覆盖，只写和全局不一样的
    "Lynae": { "heavy": 780 }
  }
}
```

时长取值优先级：**剧本单步 `duration_ms` > `character_durations` > `durations_ms`**。

> **`durations_ms` 不是游戏数据，是手感参数，而且现在只影响"同键连打"。**
> 换键的步子在 v1.3 之后完全不看这个表（游戏会让新动作直接打断旧动作）。
> 所以这张表基本只需要调 `basic` 一个值——它就是"一段普攻到底占多久"。
> 数值不需要等于动画真实帧数，只要对得上手感：连打时提示**慢半拍** → 调小，
> 提示**抢在角色前面** → 调大。某一步想单独指定，在剧本里写 `"duration_ms": 620`。
> 只有声明了 `"uncancellable": true` 的动作（长动画大招之类）才会让别的键也等。

### 怎么把时长调到准

1. 先把 `timing.enabled` 改成 `false`，正常打两三局。
2. 退出悬浮窗时，日志里会打一行 `[Timing] 本局观测到的动作节奏(毫秒)`。
3. 把里面的数字填回 `durations_ms`，再把 `enabled` 打开。

关闭时间轴时的间隔就是你的自然操作节奏，虽然混入了反应时间，但比凭空猜准得多。

### 为什么不用读内存 / 视觉识别

| 方案 | 结论 |
|---|---|
| 读游戏内存 | **不要用。** 鸣潮由腾讯 ACE 内核级反作弊保护，会检测内存读取、进程注入，并做"技能释放间隔是否符合动画帧率"的行为分析；用户协议也明确保留扫描终端内存与封禁的权利 |
| 官方插件接口 | **不存在。** 库洛只开放 BBS/抽卡记录一类的账号侧 HTTP 接口，没有实时战斗状态接口，做不了 WoW 那种官方 Addon |
| 屏幕识别 | 可行但成本高。社区开源项目 ok-wuthering-waves 走的就是 WGC 截图 + YOLO/OCR + 模拟输入，明确"不读内存、不改文件"。代价是 30fps 级别的常驻截图与推理开销、对分辨率和画面滤镜敏感、UI 改版就失效 |

而上面这两类痛点（预输入、连按、并行）**本质上不需要知道游戏状态**，只需要
一个和游戏时间线对齐的模型 —— 这就是时间轴在做的事。视觉识别更适合作为
v2.0 的"可选闭环校验"（确认技能真的放出来了、读 CD 与协奏能量），而不是前提。

## 🎭 角色差异：为什么不用"每个角色一个类"

先回答两个容易混的概念：

| 概念 | 是否随角色变化 | 说明 |
|---|---|---|
| 输入缓冲窗口 `input_buffer_ms` | **不变** | 这是引擎侧的行为（"动作没播完时的输入留多久"），同一款游戏所有角色共用一套 |
| 动作占位时长 `durations_ms` | **每角色每技能都不同** | 前摇/判定/后摇长度不同，重击蓄力能不能打断也不同。这才是差异的大头 |

所以正确的分层是**三层**，而不是继承树：

```
数据层（JSON / 表）   每角色每动作的时长、能否并行、手势要求   ← 90% 的差异在这里
规则层（通用引擎）    时间轴、缓冲、手势判定、图标查找          ← 一套代码，所有角色共用
扩展层（可选 hook）   只有当角色的机制会改变"推进规则"本身时才写
```

判断标准很简单：**差异是"数值不同"还是"规则不同"？**

- "琳奈的重击比爱弥斯长 80ms" → 数值不同 → 填 `character_durations`，不写代码
- "今汐在空中普攻时，普攻段数不会因为打断而重置" → 规则不同 → 才需要 hook

现在的落地方式：

- 数值差异 → `config.json` 的 `timing.character_durations`，只写和全局不同的项
- 单步特例 → 剧本里那一步直接写 `"duration_ms"` / `"parallel"` / `"hold"`
- 机制差异 → 在 `Director` 里加一个**可选钩子**（默认为空实现），例如
  `on_action_committed(action)`，只给特殊角色注册，不让所有角色为它买单

不推荐继承的具体理由：鸣潮角色的差异主要是**数据维度**的（时长、段数、能否并行），
不是行为维度的。按大类继承只能覆盖"法师/近战/治疗"这种粗粒度，而项目里已经证明
连"重击"这一件事在不同角色上都不一样；逐个写子类则会得到一堆只有 3 行、只改一个
数字的子类，维护成本比填表高得多。

真正需要写代码的地方通常是这几种（值得单独 hook，而不是塞进大类）：

- 形态切换改变整套普攻模组（如双形态角色）
- 空中/地面两套连段，段数进度不共享
- 某个技能会重置或保留另一条动作的进度
- 长按中途可以派生其他动作（我们的 `parallel` 就是这条的通用版本）

## 📊 如何验证内存占用

项目自带两个观测工具，不需要装第三方库：

```bash
# 1) 看某个进程当前占多少（先 --list 找 PID）
python tools/checks/mem_probe.py --list --name python
python tools/checks/mem_probe.py --pid 12345 --seconds 120 --csv mem.csv

# 2) 连续推进 8000 次连招，看内存会不会一直涨
python tools/checks/mem_bench.py --rounds 8000
```

看数字的原则：**不要只看瞬时值，要看趋势**。

- **私有内存（Private）** 才是真实占用，任务管理器里叫「提交大小」，判断泄漏主要看它；工作集会被系统回收，波动大，只能参考。
- **句柄数**应当长期平稳，持续上涨说明资源没关（比内存泄漏更早暴露问题）。
- `mem_bench` 会分段采样：每段增量越来越小 = 缓存填满后收敛（正常）；每段等量增长 = 线性泄漏。

在当前版本上实测：8000 次推进后 Qt 控件数恒定 22、动画对象恒定 5、Python 堆增量 0.00MB，私有内存在 4000 次左右稳定在 28MB 不再上涨。
